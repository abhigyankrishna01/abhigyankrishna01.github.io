Behind the build · WatchTower

The day my monitoring tool was secretly drowning.

The API looked healthy. It took requests fast and every dashboard was green. Then I compared what came in with what actually got checked.

43×

the gap between requests accepted and checks actually run

  1. 1

    Built it to look like production

    A FastAPI control plane, Celery workers, Redis and PostgreSQL, with Prometheus metrics on every check and migrations that run safely on every boot.

  2. 2

    Pushed real load through it

    Ran 50 concurrent tenants until ingestion held steady at 49.6 requests a second. p50 and p95 latency came in at 1.0s and 1.9s, and the metrics stayed within 3% of manual timing.

  3. !

    Noticed the numbers didn't add up

    Workers were only finishing 1.87 checks/s. Requests were piling up quietly behind a healthy-looking API.

  4. 4

    Traced it to the root cause

    The cause was worker thread-pool sizing, plus synchronous database calls blocking the async event loop. The fix was clear from there.

  5. 5

    Then I attacked it on purpose

    An adversarial test suite tried SSRF across 4 vectors, including cloud-metadata credential theft, and cross-tenant data access. All 20 attacks were blocked and all 40 isolation tests passed.
